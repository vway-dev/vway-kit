# {{PROJECT_NAME}} 소프트웨어 요구사항 명세 (SRS)

> 시스템이 무엇을 해야 하는가(요구사항)의 SSOT. 가장 먼저 작성. 출처: {{SOURCES}}
>
> **brownfield 는 골격으로 시작** — 미해결 슬롯은 "확인 필요"로 남기고, 요구는 사람이 말할 때
> 증분으로 채움. 코드 분석은 범위의 입력이지 요구 역산의 근거 아님(harness-rules 8-1).
>
> **두 레벨로 분리**: 고객 요구(§4)는 측정가능하진 않아도 무엇을 원하는지 명확해야 함
> ("편했으면" ✗ → "카드·간편결제 지원" ✓). 기능 요구사항(§5, FR)은 측정 가능·단일 해석
> ("빠르게" ✗ → "검색 버튼을 누르면 2초 안에 결과가 보임" ✓). 모호하거나 미상이면 지어내지 말고 `확인 필요` 명시(harness-rules 8-1).
>
> **개발자가 아닌 독자를 위해 씀**: 기획자·고객·QA 도 이 문서를 읽음. 시스템이 어떻게 해내는지가
> 아니라 사용자나 비즈니스가 관찰하는 것을 적음 — "DB 인덱스로 쿼리 최적화"는 요구가 아니라 SDS 의
> 결정. 모든 도메인 용어·약어는 용어집에 한 번 정의하고, 문서 전체에서 각 대상을 그 한 용어로만
> 부름(한 FR 의 "로그인"과 다음 FR 의 "사인인"은 두 기능으로 읽힘).
>
> **채번은 스크립트의 일**: `srs_check.py --next-id <파일> --kind <KIND>` 가 다음 번호를 냄.
> 사람도 모델도 번호를 짓지 않음. KIND 는 열린 집합 — 스크립트 어디에도 목록이 없고,
> 문서에 앵커 하나를 쓰는 것이 새 KIND 다.
